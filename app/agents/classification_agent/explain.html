How the Classification Agent Works

A person types a problem into a chat. This agent asks whatever it needs to ask, then either names the one help article that matches — or decides no article fits and passes the conversation to a human. Here is every file that takes part, in the order it acts.

app/agents/classification_agent/
01

There is only one way in

Everything outside this folder talks to the agent through a single function in main.py:

classify(conversation_id, message) main.py · the front door

Two values go in. conversation_id is the ticket number for this chat — the same value is passed on every message so the agent remembers what has already been said. message is what the person just typed.

One plain result comes back, and the caller reads two things from it: has the conversation finished, and if so, which article was found. Nothing else in this folder is called from outside.

03

Two different clocks

Some of this happens once, when the application starts. The rest happens on every single message. Mixing the two up is the usual source of confusion, so here they are apart.

Once per running app

Setting up

  • runtime_config.py reads app/config.yaml and checks every setting is sensible.
  • servicenow_kb_source.py loads kb_index.json into memory and notes every real article number.
  • foundry_agent_client.py is handed the app's existing connection to the AI service.
  • telemetry_logging.py and model_cost_meter.py are prepared for logging and cost.

Done once and kept, so the second message never pays for it again.

Every message

Answering

  • main.py receives the message and starts a stopwatch on it.
  • turn_orchestrator.py runs its loop until it has an answer.
  • foundry_agent_client.py makes the actual calls to the AI.
  • main.py shapes the outcome and hands it back.

Fast, because everything expensive was already built above.

04

One message, step by step

This is a real sequence — each step only happens after the one before it.

  1. 1
    main.py

    The chat flow calls classify() with the conversation id and the person's message. main.py borrows the connection to the AI service that the application already opened, and works out how long this whole reply is allowed to take.

  2. 2
    turn_orchestrator.py

    The message is checked against the expected shape by service_contracts.py — is there a conversation id, is there actually a message. If either is missing, it stops here rather than guessing.

  3. 3
    foundry_agent_client.py

    The message is sent to the AI agent, tagged with the conversation id so the AI can see everything said earlier in this chat. The AI replies with a small, strict answer that says what it wants to do next — not prose.

  4. 4
    turn_orchestrator.py

    The reply is read. The AI can say one of four things: ask the person something, show me the help articles, I found the article, or nothing here fits.

  5. 5
    servicenow_kb_source.py

    If the AI asked for the articles, they are fetched from kb_index.json and sent straight back to it. The AI does the choosing — nothing in this folder decides which article is right. Then the loop returns to step 3.

  6. 6
    servicenow_kb_source.py

    If the AI claims to have found an article, its number is checked against the real list first. An article number that does not exist is refused, and the AI is told to try again with a real one.

  7. 7
    main.py

    The outcome is turned into the plain result the chat flow expects, and the whole call is timed and recorded so it shows up in the app's own reporting.

Why it loops

Steps 3 to 6 repeat. That is normal: the AI usually asks to see the articles before it commits to one, so a single message from a person can involve several exchanges with the AI before there is anything to show them.

05

Three ways it can end

Every call to classify() finishes as exactly one of these. The status value says which, and it is the value the caller should act on.

follow_up

Still asking

The AI needs more detail. The question to put to the person is in the message field, and the chat stays open.

chat_close: false
kb_id: none
resolved

Article found

A real, verified article number, plus a short summary of the person's problem for whatever runs next.

chat_close: true
kb_id: KB0024755
no_match

Handed to a person

No article fits, or the agent ran out of attempts or time. The conversation ends here and a human picks it up.

chat_close: true
kb_id: none
The fourth case

If something genuinely breaks — the AI service is unreachable, for example — nothing is returned at all. main.py reports the failure upward instead, so the application shows its own "something went wrong" message rather than leaving the person in a loop that can never finish.

06

Every file, and what it is for

FileWhat it does
main.pyThe entry point. The only thing the rest of the app calls. Shapes the result and reports failures.
turn_orchestrator.pyThe loop. Runs one reply from start to finish: ask the AI, fetch articles, check the answer, decide when to stop.
foundry_agent_client.pyThe line to the AI. Sends one question, waits within a time limit, retries a stumble, records what it cost.
servicenow_kb_source.pyThe articles. Loads them once, hands them over on request, and confirms whether an article number is real.
service_contracts.pyThe shapes. Describes exactly what a valid message in and a valid answer out look like, so a malformed one is caught immediately.
runtime_config.pyThe settings reader. Loads this agent's section of app/config.yaml and rejects anything invalid at startup.
telemetry_logging.pyThe log. Writes one machine-readable line per event, all tagged with the conversation id so a chat can be traced end to end.
model_cost_meter.pyThe meter. Turns each AI reply's usage into a money figure and logs it.
backoff_retry.pyThe retry rule. When a call fails for a passing reason, waits a moment and tries again — a few times, never forever.
correlation_ids.pyThe label maker. Produces a tracking id for log lines written before a conversation id is available.
kb_index.jsonThe articles themselves. Ships with the code and is read once at startup.
07

Where the settings come from

Three places, deliberately kept separate.

A

The connection to the AI — handed in, never opened here

The application signs in to Azure AI Foundry once when it starts, and passes that same connection to every agent. This agent uses it as given. That is why no address or credential appears anywhere in this folder.

B

app/config.yaml — the agent's own dials

Which AI agent to call, how long one call may take, how many times it may fetch the articles, the price list used for cost, and the logging level. Read by runtime_config.py under the classification_agent heading.

C

Environment settings — for changing things without a redeploy

CLASSIFICATION_AGENT_NAME and CLASSIFICATION_AGENT_VERSION override the two values above. Nothing secret is ever kept in a file.

08

The guard rails

Four rules exist so a single chat message can never hang, cost an unbounded amount, or point someone at an article that does not exist.

Made-up articles are refused

Every article number the AI offers is checked against the real list. A number that is not in it is rejected and the AI is asked to correct itself.

A limit on fetches

The articles can be fetched only so many times within one reply. After that the AI is told to decide with what it already has.

A limit on the clock

The whole reply carries a deadline. When it passes, the conversation is handed to a person rather than leaving someone watching a spinner.

Stumbles are retried, failures are not hidden

A brief network problem is retried a few times with a growing pause. A real failure is reported honestly instead of being dressed up as an answer.
